## 1. `Save` 的 ODKU 带主键，撞次级唯一键时顶替另一行的身份

### 现象

表是「PK=id + 另有 UNIQUE(ip)」这种常见形状时：

```
线上：(id=1, ip="10.0.0.1", gold=999)
执行：db.Save(&Player{Id: 2, Ip: "10.0.0.1", Gold: 1})
结果：id=1 这条记录**消失**，只剩一行 id=2
```

不是"更新"，是**身份被顶替**：`ON DUPLICATE KEY UPDATE` 在任意唯一键冲突时都会触发，
命中的是主键不同的另一行，而子句里的 `` `id` = VALUES(`id`) `` 把那一行的主键就地改掉了。
零报错，`RowsAffected=2` 与正常 upsert 无法区分。

缓存那边更糟：失效只按**入参主键**算 key，`pb:<表>:1` 没人删——
后续 `FindOneByPK(1)` 会从缓存读到一条库里已经不存在的行，回源也修不好（读路径先命中缓存）。

### 根因

`valuesUpdateClause` 无条件遍历全部字段，主键照样进 `col = VALUES(col)`。
而同一个文件里的 `UpdateFieldsIfVersion` 早就在做 `pkSet` 过滤——
"SET 里不许出现主键"本来就是本仓库的既定规则，这里是唯一的破例。

### 改法

`DB.Save` / `GormDB.Save` 以及两侧保留的历史 `InsertOnDupUpdate` 入口，
不再用 ODKU 猜冲突来源，改为：

1. 按**完整主键** UPDATE 当前版本认识的全部非主键列；
2. 没命中才 INSERT；
3. INSERT 若遇到并发同主键插入，再安全重试一次主键 UPDATE；
4. 若实际撞到主键不同的备用唯一键行，返回 `ErrDuplicateKey`，不修改任何行。

`BatchSave` 逐行复用同一语义。单条批量 ODKU 无法区分冲突来自主键还是备用唯一键，
因此这里选择正确性而不是把多行强塞进一条 SQL；事务外仍是非原子，事务内由调用方统一提交。

低层 `GetSaveSQLWithArgs` 为兼容仍产出单条 ODKU，但每个非主键赋值都带完整主键守卫，
至少不会改错行；需要知道备用唯一键冲突是否发生，必须使用 `DB.Save`。

这会刻意改变「自增主键留 0、靠业务唯一键更新旧行」的旧行为：那种调用现在返回
`ErrDuplicateKey`。新自增记录用 `InsertReturningID`；按业务键合并必须显式写业务规则，
不能让一个名为 Save 的通用接口猜身份。没有主键的表同样 fail-closed。

## 2. 复用 message 连读多行，map/list 跨行串数据

`FindOneByPK` 的入参即出参，复用同一个 message 连读多行是这个 API 的天然用法。
`parseContainer` 有三条路径会带着上一行的内容返回：

```
raw == ""            → 直接 return，上一行的 map/list 原封不动留着
holder.Has 为 false  → 同上
map 分支只 Set 新键   → 上一行有、这一行没有的键**永久残留**
```

第三条最阴：这一行明明有内容，看起来一切正常，只是多了几个别人的键。

改法：函数入口统一 `reflection.Clear(fieldDesc)`，三条一起堵死；
顺带保证 Unmarshal 失败时也不会留下上一行的残值。

> `setScalarDefault` 上面那段注释早就把这个失效模式写清楚了（当时修的是 bytes/enum），
> 容器这条是同一个洞的剩余部分。

<a id="3"></a>

## 3. 真实 `oneof` 静默损坏

本库把每个字段各映射成一列，列是 NOT NULL 的，没有"这个成员没被选中"的表示：

- **写**：`SerializeFieldAsString` 对未选中的标量成员照样 `reflection.Get`，
  拿到零值，于是每个成员列都被写成 `0` / `""`，看不出谁才是被选中的那个；
- **读**：`ParseFromString` 按**声明顺序**逐个 `setFieldFromString`，
  而对 oneof 成员 `Set`（包括 `setScalarDefault` 里那次 Set 默认值）本身就会改变
  "当前选中的是谁"——于是**最后声明的成员恒胜**，真实选择被抹掉。

要正确往返就得让成员列可空、且只写选中的那一列，那是一次不兼容的结构改动。
所以在建表/对齐入口 **fail-closed**，错误信息里点名是哪个 oneof 并给出两条替代写法。

proto3 的 `optional` 在描述符里也是 oneof（synthetic），那个只是"带 has 位的普通字段"，
往返完全正常，**放行**（误伤它会让一大批正常 proto 建不了表）。

## 4. "永不收窄"有两条绕过路径

**(a) 回填注释顺带收窄。** `buildAlterClauses` 走 MODIFY 分支有两个原因，
而第二个（`fieldNum` 对不上，需要回填 `pb:N` 注释）与类型兼容性无关：
线上 `bigint`、proto 要 `int` 时 `isTypeMatch` 判"兼容、不用动"，
但只要这列还没有 `pb:N` 注释，就会因为回填注释顺带把列 MODIFY 成 `int`。
**老表恰恰普遍没有 `pb:N`**（那是后加的机制），所以这条路不是边界情况。

**(b) 改名顺带收窄。** `isRenameConvertible` 只判同族、不判宽窄，
于是 `bigint` 改名成 `int` 是"可改名"的——`CHANGE COLUMN` 连名带类型一起改，
数据在隐式转换里被截断。

改法：新增 `alignedColumnType`——目标比线上窄时**保留线上的类型本体、带上目标的属性**
（NOT NULL / DEFAULT / AUTO_INCREMENT 是 proto 侧的决定，
而 information_schema 的 COLUMN_TYPE 里没有它们），两条路径都走它，并各打一条日志。

没有去收紧 `isRenameConvertible`：那会把合法的改名一并拒掉，
而在类型合成这一层解决更准确。

<a id="5"></a>

## 5. `ExpandOnly` 派生实例漏拷 + 检查盖不全

**(a)** `WithContext` 与 `RunInTransaction` 都没把 `ExpandOnly` 带过去。
它是安全闸不是普通配置：漏拷一次，`db.WithContext(ctx).SyncAllTables()`
就在一个自以为开着闸的进程里照常执行 MODIFY / CHANGE——**闸门关着，但不生效**，
且没有任何提示。

**(b)** 检查原先写在 `buildAlterClauses` 末尾，只看得见自己产出的列子句；
而 `ADD INDEX` / `ADD UNIQUE KEY` / `ADD PRIMARY KEY` 以及跟着主键走的那条列变更
是在它之后拼出来的，**从来没有过这道闸**。

改法：检查移到 `planSchemaAlignment` 最后，覆盖本次要下发的**全部**语句。
放行标准仍是 ExpandOnly 自己的立论——**旧版本副本不会把它撤销**：
`ADD` 全家放行（本库只加不删），`MODIFY` / `CHANGE` 拒绝。
所以对既有调用方**没有行为变化**，只是原先漏检的那条 PK ALTER 现在也被盖住了。

## 6. 复合主键缓存 key 碰撞

```
("x:y", "z")  →  pb:t:x:y:z
("x", "y:z")  →  pb:t:x:y:z     ← 同一个 key
```

命中时返回的是另一行的**整条 protobuf**，而且两边互相投毒。
库里数据自始至终是对的，零日志零异常——只能靠对账发现。
字符串主键（订单号、外部账号 ID、复合业务键）里带冒号一点都不罕见。
当前 DDL 前置校验会拒绝把本库映射成 TEXT/BLOB 的 string/bytes 字段设为主键；
这里描述的是存量表、外部维护的表，或注册后未走本库新 DDL 校验的场景，缓存层仍必须防碰撞。

> **修订（2026-09-15）**：标量 string/bytes 主键现在映射成 VARCHAR（utf8mb4_0900_bin）/VARBINARY
> 整列索引，DDL 校验接受它们（只有 repeated/map/message 仍被拒）。字符串主键因此不再只出现在
> 存量或外部表里，本条的百分号编码是它们的常规路径。

改法取**最小侵入**的百分号编码：表名与每个主键分量都只转义 `%` 和 `:`。
不含这两个字符的表名/主键（整数、绝大多数字符串）产出的 key 与旧版**逐字节相同**；
含 `%` 或 `:` 的 key 会按新编码换名，这正是消除歧义所必需的行为。

但“只让少数 key 换名”**不等于可以无准备滚动升级**。新旧版本混部时，旧进程读写/删除旧 key，
新进程读写/删除 escaped key；两边不能互相失效，可能各自保留陈旧值直到 TTL 到期。升级窗口必须
先禁用这些表的缓存并 flush 受影响 key，等所有 Go/Python 实现切到新编码后再启用；或者安排所有
读写实现同步切换并清空受影响 keyspace。不能让仍用旧编码的实例与新实例继续共用缓存滚动混部。

## 7. 复合主键下批量接口只按第一列

`primaryKeyField` 只是 `primaryKey[0]`（见 `Init`），于是：

- `GormDB.BatchDelete` 发的是 `DELETE ... WHERE a IN (...)`——想删 `(a=1,b=1)` 一行，
  实际删掉 `a=1` 的**所有行**。语句成功、无报错，只是数据没了。
- `DB.FindAllByPKIn` / `GormDB.FindAllByPKIn` 同理，读回属于别的主键的行。

改法分两种：
- `BatchDelete` 改成元组 `IN`（与 `DB.BatchDelete` 一直用的正确写法对齐）；
- `FindAllByPKIn` 的签名（`[]interface{}`）**本身就表达不了复合主键**，
  所以是 fail-closed + 在错误信息里给出可照做的替代写法。

<a id="8"></a>

## 8. GORM 的 `InsertReturningID` 逃出事务

`p.DB.Connection()` 看起来正是"把这段跑在同一条连接上"的意思，
但 gorm v1.30 里它做的是：从 `*sql.Tx` 里用 unsafe 反射掏出底层 `*sql.DB`，
再从**连接池新借一条连接**。于是事务里调它，这条 INSERT 跑在事务之外——
外层 `Rollback` 覆盖不到，数据留在库里，而调用方看到的是"事务回滚了"。

改法：事务内直接用当前 `*gorm.DB`；事务外才借连接
（`LAST_INSERT_ID()` 是 session 级的，那里确实需要钉住连接）。

<a id="9"></a>

## 9. `IncrByPK` 不查列类型

MySQL 对非数值列做算术**不报错**：先把内容按数值解析（解析不出算 0）再写回。

```sql
nickname = 'abc'  →  UPDATE ... SET `nickname` = `nickname` + 1  →  nickname = '1'
```

语句成功、`RowsAffected=1`、非严格模式下零 Warning。
原先只校验"字段存在"——一个写错的列名只要**碰巧存在**就一路放行到库里。

改法：新增 `requireNumericColumn`，判据复用 `sqlbuilder.go` 既有的 `isNumericKind`
（`SQLBuilder.UpsertAdd` 早就在做同样的把关，只是其余入口漏了），
额外挡掉 repeated / map（它们的 `Kind()` 仍是元素类型，只看 Kind 会放行）。
覆盖 `DB` / `GormDB` / `SQLBuilder` 三条路径，`Assign` 上加了 `numeric` 标记。

<a id="10"></a>

## 10. GORM 的 `Save`/`BatchSave`/`InsertIgnore` 生成语法错的 SQL

`clause.OnConflict{UpdateAll: true}` 的展开发生在
`callbacks.ConvertToCreateValues`，而那段代码的第一个条件就是 `stmt.Schema != nil`。
本库走的是 `Table(name).Create(map)`：没有 Model，map 又 Parse 不出 schema，
**`stmt.Schema` 恒为 nil**。于是一条 `DoUpdates` 都展不出来，
MySQL dialector 照样写下 `ON DUPLICATE KEY UPDATE ` 然后没有下文——
发出去的是 Error 1064。`DoNothing` 分支同理。

也就是说 `GormDB.Save` / `BatchSave` / `InsertOnDupUpdate` / `InsertIgnore`
**一直是坏的**（loud failure，所以定 P1 而不是 P0）。

改法：Save/BatchSave 复用第 1 条的主键精确 UPDATE→INSERT 算法，不再依赖 GORM 的
`UpdateAll` 展开。core 与 GORM 的 `InsertIgnore` 都执行普通 INSERT，只把 MySQL 1062
转成 `(false, nil)`；不用 `INSERT IGNORE`，因为后者还会把类型截断、越界、NOT NULL
等真实错误降级成 warning。

<a id="11"></a>

## 11. 拆两条 ALTER 时漏搬自增列 → Error 1075

**这条是本轮工作区改动自己引入的回归**，不在 `v0.1.1` 里。

MySQL 要求自增列必须是键，所以那条列变更必须与 `ADD PRIMARY KEY` 同句。
拆分时的搬运判据是 `strings.HasPrefix(clause, "MODIFY COLUMN `pk` ")`——
`MODIFY` 猜中了，这两种形态全被漏掉：

```
ADD COLUMN `id` ... AUTO_INCREMENT          ← 新建自增主键列
CHANGE COLUMN `old` `id` ... AUTO_INCREMENT ← 改名成自增主键列
```

它们留在第一条 ALTER 里，在主键还不存在时带着 AUTO_INCREMENT 下发 → Error 1075，
整条 ALTER 连同**全部 ADD COLUMN** 一起失败。

改法：子句不再只是字符串。新增 `alterClause{sql, column, autoIncrement}`，
判据变成 `(列名 ∈ 主键) && 带 AUTO_INCREMENT`，三种形态一视同仁，不用猜。
不带 AUTO_INCREMENT 的主键列变更**不搬**——留在第一条反而更好，
补主键那条失败时它已经生效了。

<a id="12"></a>

## 12. 结构对齐看不见 NULL / DEFAULT / AUTO_INCREMENT / 索引列 / 主键列

原先 `columnMeta` 只有类型和字段号注释，索引只按名字比、主键只比"存不存在"。
于是"结构已对齐"这个判断是**瞎的**：

- 列在线上允许 NULL 而 proto 要 NOT NULL（或反过来）→ 判无差异；
- proto 声明了 `auto_increment_key`、线上那列却不是自增 → 判无差异，
  插入时不发号，未显式赋值的行全落到同一个值上并撞 Error 1062；
- 索引名对得上、**列组成不一样** → 判"已存在"跳过。
  这不是假想：在 `.proto` 的 index 列表**中间插一条**，
  后面所有索引的名字都往后挪一位，`idx_t_1` 这个名字还在，但它盖的是另一组列，
  于是新声明的索引**永远建不出来**，只是查询悄悄走全表扫描；
- 主键存在但**列不一样** → 判"不用补"，而按主键的读写（含缓存 key）全按 proto 走。

改法：把 `IS_NULLABLE` / `COLUMN_DEFAULT` / `EXTRA` 读回来；索引按 MySQL 的大小写不敏感
名称语义匹配，并读取唯一性、`SEQ_IN_INDEX` 列顺序与 `SUB_PART` 前缀长度；主键读取列顺序
与前缀长度。上述**已读取维度**任一不一致都返回可识别的 `ErrSchemaDrift`，不再只告警后继续启动。

这里没有声称覆盖 MySQL 索引的所有属性。当前查询不读取或比较 `IS_VISIBLE`、`INDEX_TYPE`，
也不比较 `COLLATION` 表示的升/降序；需要依赖这些属性的项目仍应由外部迁移审计兜底。

**刻意不自动修**：这里每一条的自动修法都是破坏性或会翻面的——
改 NULL/NOT NULL 与加 AUTO_INCREMENT 是 `MODIFY`（ExpandOnly 明令禁止，
且给已存在的列加自增在 TiDB 上是 Error 8200），重建索引/主键要先 DROP。
本库立场一贯是"只加不删"。缺失定义仍自动 ADD；已有定义错配则 fail-closed，
要求人工确认并迁移。

<a id="13"></a>

## 13. 三条迁移路径规划的东西不一样

只有 `DB.syncTableSchema` 会补索引和主键；
`GenerateMigrationSQL` 与 `GormDB.CreateOrUpdateTable` 只做列对齐。

后果具体到人：

- 「生成迁移脚本交 CI 审核」这条**正路**产出的 SQL 比进程自己干的事少一截——
  人按脚本迁完，进程一起来还要自己再补索引和主键，而审核时谁也没看见那些语句；
- 用 `GormDB` 的人拿到的表**结构比用 `DB` 的人少一截**，而两边都不报错。

改法：抽出纯计算的 `planSchemaAlignment`（不碰数据库，读元信息的活由各自的调用方做），
三条路径共用同一份规划逻辑。`GenerateMigrationSQL` 现在可能产出**两条** ALTER
（列+索引 / 补主键），中间用换行分隔——拆两条不是排版，是必须的执行顺序。

<a id="14"></a>

## 14. 不支持的类型先建错表、再报错

`validateFieldKinds` 只在 `buildAlterClauses` 里调，而它跑在 `CREATE TABLE` **之后**：
一个没有 MySQL 映射的字段（`sint32`/`fixed64`…）会先按默认的 `TEXT` 建出一列来，
然后函数才返回错误。表已经在库里了，事后改回正确类型是跨族 MODIFY，会把数据吃成 0。
离线生成（`tools/proto2sql`）那条路则**完全没有**这道校验。

改法：校验前移到任何 DDL 之前（`syncTableSchema` / `GormDB.CreateOrUpdateTable` /
`GenerateMigrationSQL`），并导出 `ValidateTableMessage` 供离线生成器在产出 SQL 前把关。
顺带把表名长度也纳入校验——没声明 `table_name` 时表名退化成 proto full name（含 package），
很容易超过 64 字符上限（Error 1059），这条以前是到了库里才报。

所有导出的 CREATE 入口最终都在 `MessageTable.GetCreateTableSQL` 这一层 fail-closed；
历史 string-only API 返回空串，checked API 返回具体错误。`SyncAllTables`、批量 writer 与
文件 Dump 还会先预检/完整生成整批，后一张表非法时不会先改前面的表、写半份内容或截断旧文件。

<a id="15"></a>

## 15. `USE` 与 `GET_LOCK` 走连接池

两条都是 **session 级**语句，而 `*sql.DB` 是连接池。

**`OpenDB` 的 `USE`** 只切换了它当场借到的那一条连接。冷启动后池里通常只有一条，
看起来完全正常；并发一上来就开始随机在错误的库上跑——
表现为时好时坏的 Error 1146，或者更糟：在同名的另一个库上读写成功。
`database/sql` 没有"给整个池设默认库"的接口，所以改成**校验而不是修改**：
库必须由 DSN 指定，对不上就 fail-closed 并给出可直接照做的修法。

**`GET_LOCK` / `RELEASE_LOCK`** 落在不同连接上是常态。后果比"少了个锁"更糟：
`RELEASE_LOCK` 在没持锁的 session 上返回 0（不报错），锁一直挂在最初那条连接上，
直到它被池回收——在长驻连接池里那可能是**进程的一生**。
于是别的副本每次启动都要白等 30 秒才降级，这把锁退化成了纯粹的启动延迟。

改法：持锁期间把连接**钉住**，并且**整轮结构同步都跑在这条连接上**（`DB.meta()`）。
后半句是必须的：只钉住锁、剩下的语句仍去池里另借的话，
在 `SetMaxOpenConns(1)` 的连接池上就是**死锁**——池里唯一那条连接正被锁持有者攥着，
DDL 永远借不到，两边都不超时。按副本给一条连接是常见配置，
本仓库的 `concurrency_integration_test` 也正是这么设的（这个死锁就是被它抓到的）。

<a id="16"></a>

## 16. 事务三处缺口

- **`FindMultiByWhereClauses` 写死 `p.DB`**，是全库唯一一处绕过当前事务的数据路径。
  事务内调用读到的是事务外的快照——"先改后查"查不到自己刚写的值，
  而且这条查询还持着另一条连接，与事务本身互相等锁。
- **`Transaction` 只在 `fn` 返回 error 时回滚**。一个 panic 会带着未提交的事务穿过去，
  那条连接被 `database/sql` 一直算作"事务中"，既不回滚也不归还池子；
  攒够几次连接池就被僵尸事务占满，而它们在 InnoDB 里还持着行锁——
  表现为整个服务卡在拿连接上，与真正的根因（某处 panic）看不出任何关系。
  改法是哨兵标志 + `defer` 兜底回滚，并 `recover`→`Rollback`→**原样重抛**。
- **`GormDB` 的 `QueryOptions.ForUpdate` 被整个忽略**：
  调用方期待"读到加锁后的最新值"，发出去的却是一条普通 SELECT，
  "先锁后改"退化成读-改-写，并发下丢更新。而 `DB` 侧同一个选项是生效的。

<a id="17"></a>

## 17. 分批写入中途失败时，已提交批次不失效缓存

分批不是原子的：事务外每批各自提交，第 3 批失败时前 2 批**已经在库里了**。
失效原先写在循环外，于是那 2 批的缓存一条都没删——库是新值、缓存是旧值，
而调用方拿到的是 error，多半会当作"整个批次没写进去"，谁也不会回来清缓存。

改法：`BatchSave` / `BatchDelete` 每批成功就立刻失效这一批。
事务内不受影响（`invalidateMessages` 会攒进 `pendingCacheDels`，提交后统一删）。

顺带修了 `InvalidateCache`：它原先无条件立即 `Del`，
在事务里先删缓存、事务再回滚的话，写路径特意做的"先写库后删缓存 + 回滚不删"
在这条手动入口上整个被绕过。

<a id="18"></a>

## 18. CLI 三条

- **输入被同名文件顶掉。** `resolveInputs` 把 `-proto a/b/game.proto` 降成裸文件名，
  再把 `a/b` 追加到搜索路径**末尾**。任何一个 `-I` 目录里的同名文件都会先命中——
  用户明明写了路径，编译的却是另一个文件。
  改法是**先算一遍谁会赢**，赢的不是用户点名的那个就报错并把两边路径都打出来
  （不去改解析顺序，那会连带影响 import 的解析语义）。
- **路径穿越。** `-single` 与 proto 里的 `table_name` 都被直接
  `filepath.Join(outDir, name)`，而 `Join` 会把 `..` 规规矩矩地解析掉，
  于是 `-out` 这道边界形同虚设。改法是 `checkOutputName`。
- **表注释转义依赖 SQL mode。** 表名不是绑定参数、是直接拼进 DDL 的。
  一个以反斜杠结尾的表名就能把字符串提前闭合（`COMMENT 'evil\'`），
  而连接默认开着 `MultiStatements`，缝隙足以追加语句。
  改法是先双写反斜杠，再用 SQL 标准的 `''` 倍写单引号；这样默认模式与
  `NO_BACKSLASH_ESCAPES` 都不会让引号逃出 COMMENT 字面量。

  > `MultiStatements=true` **保留**：`FindMultiByWhereClauses` 依赖它。
  > 注入面在于表注释这个非参数拼接点，转义修好就闭合了。

<a id="20"></a>

## 20. `Save` 并发分类必须用当前读核对整行

第一次按主键 UPDATE 没改到行、INSERT 又撞 1062 后，重试 UPDATE 的 `RowsAffected=0`
有两种含义：目标主键仍不存在，或数据库里已经是完全相同的值。原修复用普通
`ExistsByPK` 区分；但 MySQL 默认 REPEATABLE READ 事务里，UPDATE 是 current read，
后面的普通 SELECT 却可能还停留在旧快照，于是把真实存在的同行误报成备用唯一键冲突。

而事务外只查“主键存在”也有 TOCTOU：重试 UPDATE 与 SELECT 之间若插入了一条同主键、
不同内容的行，Save 会误报成功。最终改成带 `FOR UPDATE` 的 current read，并用 NULL-safe
等值条件核对本版本认识的**全部列**；只有数据库当前行与目标值一致才算幂等成功，
否则保留 `ErrDuplicateKey`。

终审又补到一个 MySQL 类型提升边界：protobuf 标量以十进制字符串作为参数下发，
而 `FLOAT` 列直接与该参数比较时会提升精度，MySQL 8.4 中
`CAST(0.1 AS FLOAT) <=> '0.1'` 为 0。分类参数现在在 Go 侧先恢复成真实 float32
存储精度，再以数值参数绑定；没有使用 MySQL 8.0.17 才支持的 `CAST(... AS FLOAT)`，
保留 5.7 兼容，并用真实 MySQL 回归覆盖“同 PK、同 float 值连续 Save”不会误报冲突。

<a id="21"></a>

## 21. 类型与改名属性都必须 fail-closed

“永不收窄”只解决同族宽窄问题，不代表跨族转换安全。线上 `MEDIUMTEXT`、proto 改成
`INT` 时，旧逻辑仍会自动 `MODIFY`，MySQL 可能把整列文本转成 0。现在同名列跨族也返回
`ErrUnsafeSchemaConversion`，只允许同族安全拓宽；转换语义交给人工迁移。

另一个漏口在按 `pb:N` 改名：漂移检查只按**新列名**查元数据，找不到就当成“将新增”，
所以旧列的 NULL / DEFAULT / AUTO_INCREMENT 错配全被跳过，随后 `CHANGE COLUMN` 又顺手
改属性。现在漂移检查与改名规划用同一套字段号定位规则，属性不一致先返回
`ErrSchemaDrift`，不会用一次改名夹带数据语义变化。

<a id="22"></a>

## 22. 锁竞争与 GORM 当前库校验

`GET_LOCK` 返回 0 的含义不是“函数不支持”，而是另一个同步者仍持锁、等待已超时；
此时继续无锁 ALTER 正好重建了咨询锁要消除的竞态。现在 0 / NULL 与非兼容性查询错误
都会中止同步；只有能识别为兼容实现不提供该函数时才允许有边界地降级。

GORM schema bridge 原先拿到 `*sql.DB` 后直接赋 `core.DBName`，绕过了 `DB.OpenDB` 的
`SELECT DATABASE()` / `lower_case_table_names` 校验。若连接实际在库 A、调用方却传库 B，
元数据从 B 规划，未限定名的 ALTER 在 A 执行。现在 bridge 同样走 `OpenDB`，库名不一致时
在任何 DDL 前 fail-closed。

core 的单表/全表同步入口也拒绝从 `RunInTransaction` 的 `tx *DB` 调用。DDL 与咨询锁原本
会绕开业务 `*sql.Tx` 走一条新 session，外层即使回滚，schema 也已经提交；现在统一返回
`ErrSchemaSyncInTransaction`，与 GORM bridge 的事务内 fail-closed 规则一致。

<a id="23"></a>

## 23. 自增主键列与依赖索引必须保持拓扑顺序

缺失的自增主键列会与 `ADD PRIMARY KEY` 一起挪到第二条 ALTER；但初版仍把引用该列的
缺失二级/唯一索引留在第一条，先执行 `ADD INDEX (...id...)` 就报 Error 1072。
现在只要本轮有自增主键列被后移，其依赖的缺失索引也跟到主键 ALTER，顺序固定为
“列存在 → 主键成立 → 二级/唯一索引”。

<a id="24"></a>

## 24. TableOption 是 DDL 输入，也要前置校验

字段 kind 合法不等于整张表配置合法。`WithPrimaryKey("typo")`、
`WithIndexes("missing")`、把自增指向不存在/非整数/未被键覆盖的列，过去都能通过
`GenerateCreateTableSQLChecked`，产出必然报 1072/1075 的 SQL；nullable 主键还会造成
建表后永久 schema drift。现在主键、普通索引、唯一键、自增与 nullable 引用统一在
任何 DDL 前校验，checked API 返回具体错误，历史 string-only API 继续 fail-closed 返回空串。

终审补齐了两个配置边界：空/全空白 `table_name` 会在生成 ``CREATE TABLE ```` 前拒绝；
映射成可空或只能做前缀索引的字段也不能当主键。后者既避免 MySQL 静默把列改成
`NOT NULL` 后每次同步都报 drift，也避免两个只在第 192 个字符后不同的 TEXT 值被当成
同一个主键。当前库会把 string/bytes 映射为 MEDIUMTEXT/MEDIUMBLOB，因此不能将其声明为主键；
需要字符串身份时，建议使用数值代理主键，把字符串保留为业务列。

> **修订（2026-09-15）**：主键/唯一键里的标量 string/bytes 已改为映射成 VARCHAR（utf8mb4_0900_bin）/
> VARBINARY 整列索引，可以声明为主键；只能落 BLOB 前缀索引的 repeated/map/message 字段继续被拒，
> 可空主键的拒绝理由不变（键列同样禁止 nullable）。数值代理主键 + `(provider, provider_id)`
> 唯一键仍是推荐形态，见 README「字符串键（第三方 ID）」。

<a id="25"></a>

## 25. 物理表名与输出路径按可部署环境判重

生成器原先只按精确字符串去重，`Users` 与 `users` 在 Windows 会落到同一个文件，后者
静默覆盖前者；在 `lower_case_table_names != 0` 的 MySQL/TiDB 上也指向同一物理表。
现在 table_name 按大小写不敏感的可移植口径判重，逐表输出还拒绝 Windows 保留设备名、
非法字符与尾随点/空格。

运行时注册表以 proto full name 为 key，所以两个不同 message 仍可能通过
`WithTableName` 映射到同一物理表。`WriteCreateTableSQL` / `WriteMigrationSQL` 现在会在
写 writer 或读取数据库前统一拒绝，并给排序增加完整 tie-break，杜绝 map 迭代顺序决定
哪份 `CREATE TABLE IF NOT EXISTS` 先被执行。`WriteMigrationSQL` 同一 message 重复传入也
会在 I/O 前拒绝，避免产出两份相同 `ALTER`（第一份成功、第二份必然撞重复列/索引）。

<a id="26"></a>

## 26. 多文件替换有明确 commit point

文件全部安装完成后，旧备份的删除属于 post-commit cleanup；此时部分备份可能已经删掉，
再声称“观察到任何错误都能回滚”并不成立。cleanup 现在会尽量处理全部备份，并以可识别的
“输出已提交、清理未完成”结果返回；CLI 把它报告为 warning，而不是误导调用者认为旧输出
仍完整保留。安装 commit point 之前的准备/rename 失败仍按原逻辑恢复所有可恢复的旧文件。

<a id="27"></a>

## 27. 终审边界：数值谓词、配置解析与元数据身份都要无歧义

最后一轮从已经修好的路径继续向外追，补到七组不能靠“字符串看起来一样”判断的边界。

**(a) 数值谓词不能继续绑定十进制字符串。** protobuf 标量的稳定序列化值是字符串，
用于 INSERT/UPDATE 赋值没有问题；但拿它直接与数值列做 WHERE、IN 或 CAS 比较时，MySQL
会发生隐式数值提升。`BIGINT` / `BIGINT UNSIGNED` 超过 `2^53` 后，相邻整数可能经 DOUBLE
折叠成同一个值，导致按主键/KV读取、保存或删除命中相邻账号；`FLOAT` 则会出现第 20 条所述的
存储精度与字符串比较精度不一致。现在库生成的主键谓词、KV helper、主键/KV IN、版本 CAS
与 Save current-row 分类会按 descriptor 把参数恢复为精确的 `int64` / `uint64` / `float64`
等 driver 类型；`float` 会先按 float32 存储精度规范化。调用方自己写的裸 `whereClause`
仍由调用方负责参数类型，本库不会猜 SQL 表达式里的列。

**(b) SQL 参数类型与缓存 key 的 canonical 表示必须分开。** SQL 侧需要 typed 参数，缓存侧却要
保持升级前的稳定十进制/字节表示；若两者共用同一份值，bool key 会从 `1` 变成 `true`，
float key 也可能换成长小数，旧缓存会被整批搁浅。现在缓存直接使用
`primaryKeySerializedValues` 的 canonical 值，SQL 再经 `primaryKeyValues` 做类型规范化；
第 6 条新增的 `%` / `:` 转义之外，普通旧 key 保持逐字节兼容。含转义字符的 key 在新旧版本
混部时仍须按第 6 条禁用/flush 缓存或同步切换，typed 参数解耦不会消除那段升级窗口。

**(c) 浮点数不能作为稳定身份。** `FLOAT` / `DOUBLE` 的十进制、二进制与数据库比较语义并不
适合作为主键契约，因此 `WithPrimaryKey` 在任何 DDL 前统一返回 `ErrInvalidTableOption`；
普通非主键浮点列仍然支持。身份字段应改用整数或枚举。

**(d) descriptor option 不能替调用方吞掉空项。** 代码级 `WithPrimaryKey("id", "", "port")`
已经会失败，但 descriptor 解析原先把 `primary_key="id,,port"` 压成 `id,port`，把
`index="id;;port"` 压成两个索引，绕过了同一套校验并静默改变 schema。解析层现在保留空分量，
统一交给 table validator 以 `ErrInvalidTableOption` fail-closed。同一入口也会在 DDL 前拒绝零字段
message 和超过 MySQL 64 字符上限的列名，避免生成必失败或没有业务身份的表结构。

**(e) `pb:N` 与物理表映射都必须唯一。** 线上若两列带同一个 `pb:N`，即使确定性挑一列也无法
知道哪个才是真实数据；现在确定性报 `ErrSchemaDrift` 并列出冲突列。两个不同
message 若以仅大小写不同的名字映射同一物理表，则不仅 writer/sync 会冲突，预建表场景的 DML、
缓存 key 与列表查询也会让两套 descriptor 共享同一份数据。core 与 GORM 的运行时解析现在都在
任何数据库/缓存 I/O 前返回 `ErrDuplicateTableMapping`。

**(f) 索引名按 MySQL 语义匹配，定义只承诺实际读取的维度。** `IDX_T_0` 与 `idx_t_0` 是同一个
索引，不能再生成第二条 `ADD INDEX`；命中后继续核对唯一性、列顺序和前缀长度。当前不核对
`IS_VISIBLE`、`INDEX_TYPE` 或 `COLLATION` 表示的升/降序，边界与第 12 条一致，文档不再把它
描述成“完整索引定义”。

**(g) 列名也按 MySQL 大小写不敏感语义定位。** 存量表若是 `ID`、descriptor 字段是 `id`，且
旧列还没有 `pb:N` 注释，精确 map lookup 会误判缺列并生成必然撞 1060 的 `ADD COLUMN id`，漂移
检查也会漏掉原列。现在列解析与索引名一样按大小写折叠匹配；若元数据中出现折叠后不唯一的候选，
直接以 schema drift fail-closed，绝不任选一列。

对应回归包括 `TestNumericPredicatesBindExactDriverTypes`、
`TestUint64PredicatesDoNotCollapseAboveDoublePrecision`（真实 MySQL/TiDB gated）、
`TestCacheKeyKeepsCanonicalBoolEncoding`、`TestFloatPrimaryKeyFailsClosed`、
`TestDescriptorPrimaryKeyEmptyComponentFailsClosed`、`TestDescriptorIndexEmptyComponentFailsClosed`、
`TestInvalidTableShapesFailBeforeDDL`、`TestDuplicateFieldNumberMetadataFailsClosed`、
`TestIndexNamesAreCaseInsensitiveDuringSchemaSync`、`TestColumnNamesAreCaseInsensitiveDuringSchemaPlanning`、
`TestCaseFoldedColumnAmbiguityFailsClosed`、`TestCaseInsensitiveColumnMatchStillChecksAttributeDrift` 与
`TestRuntimeSchemaSyncRejectsDuplicatePhysicalTableMappingsBeforeIO`。
